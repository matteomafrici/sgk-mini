# Validation

Reproducible validation of the sgk-mini stack.

## Linux PicoGK setup

The project pins PicoGK 2.2.0, which loads native runtime 26.2. Build that
runtime from the [matching PicoGKRuntime source revision](https://github.com/leap71/PicoGKRuntime/tree/0f26321c18ed878a7820ef769c38fd5d49d39242).
The commands below use the build configuration exercised on Arch/Omarchy.
On other Linux distributions, use the equivalent development packages.

Install Git, the .NET 9 SDK, a C++ compiler (GCC 16 was used), CMake, Ninja,
and pkg-config. The build also uses Boost, oneTBB, Blosc, zlib, OpenGL,
and GLFW's X11 and Wayland development dependencies. On Arch/Omarchy the
build used `cmake`, `ninja`, `boost`, `glfw`, `blosc`, and
`extra-cmake-modules` along with the system graphics and development packages.

Run these commands from the SGK Mini repository root. The native checkout goes
alongside SGK Mini. The recursive submodule checkout supplies OpenVDB, GLFW,
and ImGui at the revisions expected by the native runtime.

```bash
git clone https://github.com/leap71/PicoGKRuntime.git ../PicoGKRuntime
git -C ../PicoGKRuntime checkout --detach 0f26321c18ed878a7820ef769c38fd5d49d39242
git -C ../PicoGKRuntime submodule update --init --recursive
cmake -S ../PicoGKRuntime -B ../PicoGKRuntime/build -G Ninja
cmake --build ../PicoGKRuntime/build --parallel 2

dotnet build src/SGK.Geometry/ -c Debug
runtime_dir=src/SGK.Geometry/bin/Debug/net9.0
cp ../PicoGKRuntime/build/lib/picogk.so "$runtime_dir/"
for name in picogk.26.2 libpicogk.26.2 picogk.26.2.so libpicogk.26.2.so; do
  ln -sfn picogk.so "$runtime_dir/$name"
done
ldd "$runtime_dir/picogk.so"
```

Install any dependency that `ldd` reports as `not found`. Run the geometry
check from a graphical Linux session with a writable `~/Documents/`
directory for PicoGK's log. The viewer still opens with `--auto-exit`.

## Analytical (geometry → feature → physics)

The C# stage generates the hollow-cylinder voxel geometry, extracts features,
and writes the analytical annular-flow benchmark:

```bash
dotnet run --project src/SGK.Geometry/ -- --auto-exit
```

Outputs land in `output/` (gitignored). The runtime asserts the invariants
(schema, voxel round-trip, laminar regime, wall no-slip) and fails loudly if
they break.

### Geometry command options

`--auto-exit` closes the PicoGK viewer when the task finishes. Omit it to
inspect the geometry in the viewer. `--config <file.json>` overrides the
case inputs. Unknown configuration properties are rejected. For example,
save the following as `annulus.json`:

```json
{
  "CaseId": "ann-001",
  "OuterRadiusMm": 12.0,
  "InnerRadiusMm": 9.0,
  "LengthMm": 40.0,
  "VoxelSizeMm": 0.2,
  "VolumetricFlowRateM3PerS": 0.000002
}
```

```bash
dotnet run --project src/SGK.Geometry/ -- --auto-exit --config annulus.json
```

An optional `OutputDirectory` sets the destination. With the default
configuration, `output/` in the repository receives three files:

| File | Contents |
| --- | --- |
| `hollow-cylinder.vdb` | Voxel field, saved and reloaded for the round-trip check |
| `hollow-cylinder.features.json` | Case ID, schema, voxel size, volume, and bounding box |
| `hollow-cylinder.physical-case.json` | Reconstructed radii, fluid properties, velocity profile, pressure drop, and signed wall shear stresses |

The analytical model recovers the inner radius from the measured voxel
volume and bounding-box dimensions. At 0.2 mm voxel size it recovers
7.9993 mm against the nominal 8 mm. See the
[voxel resolution measurements](voxel-resolution-curve.md) for the trade-off
between pitch, runtime, memory, and volume error.

## CFD cross-check (OpenFOAM)

`openfoam/annulus_cyclic/` is a self-contained OpenFOAM case for steady,
fully developed, laminar axial flow in a concentric annulus. It uses cyclic
periodic boundaries with `meanVelocityForce`, which removes developing-flow
artifacts and gives one identical solution at every cross-section.

Only the dictionary sources are versioned; `constant/polyMesh/`, the time
directories and logs are generated by `run_annulus.sh` and gitignored.

Prerequisites:

- OpenFOAM v2606 with its environment available via `etc/bashrc`
  (default `~/opt/OpenFOAM/OpenFOAM-v2606/etc/bashrc`, override with
  `FOAM_BASHRC`).
- A Python with numpy (default `~/data/venvs/sgk-mini/bin/python`, override
  with `PYTHON`).

Run:

```bash
dotnet run --project src/SGK.Geometry/ -- --auto-exit   # benchmark first
./validation/run_annulus.sh                             # blockMesh + simpleFoam + report
./validation/run_annulus.sh --check                     # non-zero exit on drift
```

`validate_annulus.py` compares the solver field against the closed-form
solution. It reads the pressure gradient from the solver log (no magic
numbers) and the benchmark from `output/hollow-cylinder.physical-case.json`.

### Reference result (Omarchy, 2026-11-18)

2° axisymmetric wedge, 58×100×1 cells, axial periodicity, 8000 iterations,
voxel size 0.2 mm:

| Metric | Value |
|---|---|
| mean \|err\| / Umax | 0.0046 % |
| max \|err\| / Umax | 0.0071 % |
| Umax error | 0.010 % |
| pressure-gradient error | 0.0095 % |
| flow-rate error (native flux / saved field) | 0.020307 / 0.020306 % |
| mesh sector-area defect | −0.0203 % |

The flow-rate error is now the measured geometric defect of the finite wedge,
not an unattributed residual: the end faces are polygons with
`sin(2°)/2° = 0.0203 %` less area than the true annulus, and the native patch
flux misses Q by the same 0.0203 %. The defect is measured from the cell
volumes and reported, not corrected away.

The profile is compared at the radius of the radial cell faces. The raw cell
centre of the innermost cell sits at `r_face·cos(1°)`, which is *inside* the
ideal wall; evaluating the analytical solution there is an extrapolation outside
its domain. The audited 3.64 %/7.15 % profile error came from that mismatch, not
from the finite-volume scheme, and the claim that it was inherent second-order
error was wrong. With a consistent radius the remaining error is 0.0046 % on
average and 0.0071 % at worst, measured on the new mesh.

The peak velocity is compared against the continuous analytical maximum
(evaluated where `du/dr = 0`), not against the largest of the 17 profile
samples. The sampled peak understates the true peak by about 0.03 % and is kept
in the record as `SampledMaxVelocityMPerS` for traceability.

**Every literal number that connects the geometry record to the CFD case** is
checked before the mesh is built:

| Constant | Where | Why it matters |
|---|---|---|
| `Ri`, `Ro` | `system/blockMeshDict` | the solver would compute a different shape |
| `L` | `system/blockMeshDict` | the pressure drop would be scaled to another length |
| `nu` | `constant/transportProperties` | the profile would be the solution for another fluid |
| `Ubar` (all three components) | `constant/fvOptions` | the solver would impose a different mean velocity, including a transverse one the analytical case does not have |
| `CaseId` | `case.json` | a swapped or stale case would be compared against another record |

`validate_annulus.py --check-inputs` runs before `blockMesh` and refuses to
continue if any of them disagrees with
`output/hollow-cylinder.physical-case.json`. `validation/test_guards.py` breaks
each one on purpose and requires the guard to reject it.

**How this guard was earned.** When the voxel size moved from 0.3 to 0.2 mm the
radii were updated but `Ubar` was not, and it kept the mean velocity of the
previous record: 0.0088648 m/s against the required 0.0088393 m/s, i.e. 0.29 %
too high. On the old 30° mesh every metric moved by about that amount:

| Metric (old 30° mesh) | with the stale `Ubar` | with `Ubar` consistent |
|---|---|---|
| Umax error | 0.278 % | 0.011 % |
| pressure-gradient error | 1.04 % | 0.74 % |
| flow-rate error | 0.50 % | 0.78 % |

Nothing was wrong with the mesh or with the geometry. A constant copied by hand
had gone stale, and the only symptom was that the comparison moved quietly. An
earlier explanation — that the previous numbers were flattered by a 3 µm radius
error cancelling a 0.507 % area bias — was wrong and has been removed: mesh and
benchmark used the same radii in both cases, so that error cancelled in both.

### Convergence

Reaching `endTime` is not counted as convergence. The validator records the
residuals, the iteration count and the stopping reason, and requires the `Ux`
residual below its target, the `p` residual below its target (or a pressure
field negligible against `dpL/rho·L`), negligible absolute transverse velocity,
a closed continuity error, and stable `dpL`, `Q` and `Umax` between the last two
saved times. The p qualification is recorded in `docs/pilot-checks.md`: in this
periodic case `p` is ~1e-15 because the gradient lives in `meanVelocityForce`,
so its normalised residual divides by a near-zero denominator and cannot reach
`1e-3`.
